# 多轮会话历史图片上下文说明

- 状态：简化版已实现
- 问题记录日期：2026-07-22
- 简化版确认日期：2026-07-23
- 影响范围：创作台同一会话内的连续生图与图片编辑请求

## 1. 问题背景

AI Image Studio 使用会话承载连续创作。旧实现虽然会把当前分支最近的历史文本拼入 Prompt，但只有用户输入命中“上一张、保持、继续、改成、换成”等固定关键词时，才会把上一轮图片作为真实图片输入提交给 Provider。

因此，“人物不像”“再自然一点”“表情不对”等明显依赖上一轮图片、但没有命中关键词的续问，仍可能被当作纯文生图请求。上游 Images API 不会根据本地 `conversationId` 自动取得历史图片，只传文字“已生成图片”也不能替代真实图片文件。

## 2. 当前简化方案

当前阶段不引入 LLM 规划器，不实现 Agent 模式，也不做自然语言意图分类。后端采用固定、可预测的规则：

1. 创建任务时，查询同一会话中最近创建且状态为 `succeeded` 的任务。
2. 该任务有图片结果时，只选择 `result_index` 最小的首张结果作为历史图片上下文。
3. 不再检查本轮 Prompt 是否包含续问关键词；只要会话中存在上述图片，就自动携带。
4. 本轮用户手动上传的参考图继续保留，历史上下文额外最多追加一张；同一 Asset 已被本轮显式选择时不重复追加。
5. 本轮显式参考图和自动历史图合计最多 10 张，超过时拒绝创建任务并提示用户减少参考图。
6. 有任意输入图片时，任务 `operation=edit`；会话中没有历史图片且本轮没有上传图片时，任务 `operation=generation`。
7. 实际选中的 Asset ID 继续写入 `request_params.context_asset_ids` 和 `task_input_images`，便于重试、审计和问题复现。
8. 历史图片仍通过统一 Asset 存储层读取，因此 Local 与 S3 文件使用同一条 Provider 输入链路。

历史文本上下文保持现有逻辑：沿当前消息分支读取最近 8 条非空用户/助手文本并与当前请求拼接。本次简化只调整历史图片选择规则。

## 3. 决策流程

```text
本轮创建任务
    ↓
保留本轮手动上传的参考图
    ↓
同一会话是否存在成功任务的图片结果？
├─ 否：不追加历史图片
└─ 是：取最近成功任务的首张结果
         ├─ 已在本轮参考图中：不重复追加
         └─ 未在本轮参考图中：追加为唯一历史图片
    ↓
最终没有输入图片 → generation
最终存在输入图片 → edit
```

## 4. 验收标准

1. 新会话首次输入且未上传图片时，任务必须为 `operation=generation`，`context_asset_ids=[]`。
2. 同一会话已有一轮成功图片后，无论下一轮输入是否包含“继续、上一张”等关键词，都必须携带该图片并使用 `operation=edit`。
3. 最近成功任务生成多张图片时，只携带其 `result_index` 最小的首张结果。
4. 本轮上传参考图时，参考图与最近历史图都必须提交；历史图最多一张。
5. 本轮显式选择的图片正好是最近历史图时，不得重复写入 `task_input_images`。
6. 最近一轮任务失败、取消或仍在处理中但没有成功结果时，必须回退到更早的最近成功任务；从未成功生成过图片时不携带历史图。
7. `request_params.context_asset_ids`、`task_input_images.input_role` 和最终 `operation` 必须能够解释本轮实际提交给 Provider 的图片。

## 5. 当前限制

- 该方案是应用层连续图片编辑，不是 Responses API `previous_response_id` 意义上的 Provider 原生多轮会话。
- 系统不会判断用户是否想在原会话中“全新创作”。只要会话已有成功图片，后续请求都会基于最近图片编辑；需要完全不参考旧图时，当前应新建会话。
- 一轮生成多张图片时暂不理解“第二张”等自然语言选择，固定使用该轮首张结果。
- 如果用户在上一轮图片尚未生成完成时立即发送下一轮消息，提交当时没有可用成功图片，本轮不会等待上一轮完成后再补充图片。
- 后续如需更准确的意图判断、图片选择和原生多轮，可另行增加显式“全新创作”操作、LLM 规划器或 Responses API 会话模式；这些均不属于当前简化版。

# 多轮会话历史图片上下文问题说明

- 状态：待产品与技术方案确认
- 记录日期：2026-07-22
- 影响范围：创作台同一会话内的连续追问、人物/主体一致性、图片编辑请求
- 本文性质：已知问题与候选方案记录；当前不修改运行逻辑

## 1. 问题背景

AI Image Studio 以会话和消息分支承载多轮创作。产品预期是：用户在上一轮已经生成图片后，可以直接继续提出“人物不像”“再自然一点”“换一个姿势”等要求，系统应结合当前分支的历史文本和必要历史图片完成下一轮生成，而不是把每一轮都当作互不相关的文生图请求。

实际场景中，上一轮已成功生成目标人物图片，用户随后输入“这不是目标人物，一点都不像”。下一轮虽然携带了历史文本，但没有把上一轮生成图片作为图片输入发送给模型，人物一致性因而无法得到保障。

## 2. 实际证据

2026-07-22 12:28:16 对应任务的持久化请求快照显示：

| 字段 | 实际值 | 含义 |
|---|---|---|
| `operation` | `generation` | 走纯文生图，而不是图片编辑 |
| `context_message_count` | `4` | 携带了当前分支最近 4 条历史文本 |
| `context_asset_ids` | `[]` | 没有携带任何历史图片 Asset |

最终文本 Prompt 的结构为：

```text
Conversation context:
User: 第一轮用户要求
Assistant: 第一轮失败提示
User: 第二轮用户要求
Assistant: 已生成 1 张图片
Current request: 这不是目标人物，一点都不像
```

这说明当前实现具备文本多轮能力，但在该类自然追问中没有形成图片多轮能力。`Assistant: 已生成 1 张图片` 只是文字，不包含上一轮图片的像素或视觉特征，不能替代真实图片输入。

## 3. 当前实现逻辑

1. Web 端提交当前可见分支末端的助手消息 ID 作为 `parentMessageId`。
2. 后端沿 `parentMessageId` 递归读取当前分支，最多保留最近 8 条有文本的用户/助手消息。
3. Context Builder 把这些历史文本和当前请求拼接为一个最终 Prompt。
4. 本轮用户明确上传的参考图始终作为输入图片。
5. 没有明确上传图片时，只有当前请求命中固定关键词，才尝试选择父助手消息生成的图片。
6. 当前关键词包括“上一张、上张、保持、继续、改成、换成、previous、keep、continue、change it、make it”。
7. 选中历史图片后任务才切换为 `edit`，并由存储层从 Local 或 S3 读取真实文件交给 Provider Adapter。

## 4. 根因

### 4.1 图片上下文依赖固定关键词

“不像”“更自然一点”“表情不对”“再年轻一些”等明显依赖上一轮图片的反馈，没有命中当前关键词集合，因此被错误识别为全新的 `generation` 请求。

仅继续增加关键词只能缓解个别表达，无法覆盖自然语言的长尾形式，也难以支持多语言。

### 4.2 文本上下文与图片上下文策略不一致

历史文本默认沿当前分支加载；历史图片却需要额外的关键词触发。用户看到的是同一会话连续问答，但后端实际只保证了文本连续性。

### 4.3 助手失败消息也可能进入文本上下文

当前文本查询按角色与非空内容筛选，没有排除失败或取消的助手消息。“生成失败，请重试”等运行状态文本进入上游 Prompt，会产生无意义噪声。

### 4.4 上游 Images API 不会自动理解本地会话

OpenAI Compatible Images API 等上游接口通常把每次请求当作独立请求。平台必须显式提交最终文本 Prompt 和图片文件；只传本地 `conversationId` 或文字“已生成图片”不会让上游自动获得历史图片。

## 5. 候选方案

| 方案 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| 扩充关键词 | 修改小、上线快 | 仍会漏判，维护成本持续增长 | 仅作为临时补丁 |
| 每轮发送全部历史图片 | 实现直观 | 成本、延迟和隐私范围扩大，容易超过模型限制 | 不采用 |
| 同一分支续问默认携带最近一轮有效结果 | 符合聊天心智，能解决“人物不像”等反馈 | 需要识别明确的全新创作意图 | 推荐作为默认规则 |
| 引入轻量意图分类器 | 对自然语言覆盖更好 | 增加复杂度和误判来源 | 后续增强，不作为首个修复 |
| 增加显式“沿用上一轮/全新创作”模式 | 行为最可控、易解释 | 增加一个用户决策点 | 可与推荐默认规则组合 |

## 6. 推荐解决方案

采用“会话分支默认连续 + 明确重置”的规则，不再把固定关键词作为唯一入口。

1. 本轮有用户上传图片时，以本轮图片为最高优先级，不再自动追加历史图片。
2. 本轮没有上传图片、父助手消息存在且只有一个有效生成结果时，默认把该结果作为 `context_asset_ids`，任务按 `edit` 执行。
3. 用户明确表达“全新创作、不参考上一张、重新从文本生成”等重置意图时，不携带历史图片，按 `generation` 执行。
4. 父助手消息有多张结果时：能从“第一张、第二张”等表达唯一定位则选择对应图片；无法唯一定位时不发送全部图片，应提示用户明确目标。
5. 只从当前可见消息分支选图，禁止跨分支或跨会话误取图片。
6. 只允许选择状态为有效完成、文件仍可读取且归属当前用户的 Asset。
7. 文本上下文排除失败、取消和纯运行状态助手消息；较长会话继续使用数量或 Token 预算截断。
8. 在任务快照中增加或固化 `context_strategy`、`context_message_ids`、`context_asset_ids` 和最终 `operation`，便于审计与问题复现。
9. Provider 或模型不支持图片编辑时，前端应明确提示无法保持上一轮图片一致性，不应静默降级为普通文生图。

该方案仍然不会把会话全部图片发送给上游，符合最小上下文、最小成本和最小隐私暴露原则。

## 7. 推荐决策流程

```text
本轮显式上传图片？
├─ 是：使用本轮图片 → edit
└─ 否
   ├─ 用户明确要求全新创作：不带历史图片 → generation
   └─ 当前分支父助手有有效生成结果？
      ├─ 无：不带历史图片 → generation
      ├─ 仅一张：默认携带该图片 → edit
      └─ 多张
         ├─ 指令可唯一定位：携带目标图片 → edit
         └─ 无法定位：提示用户明确选择，不猜测、不全量发送
```

## 8. 验收标准

1. 上一轮只有一张成功图片时，输入“人物不像”“再自然一点”等不含旧关键词的续问，任务快照必须记录上一轮 Asset ID，且 `operation=edit`。
2. 输入“全新创作一张海边日落”时，不得携带上一轮图片，且 `operation=generation`。
3. 上一轮存在多张图片且用户说“把第二张改成夜景”时，只携带第二张。
4. 多张图片无法唯一定位时，系统必须提示用户补充说明，不得随机选择或发送全部图片。
5. 切换消息分支后，只能使用当前分支的历史文本和图片。
6. 失败、取消消息不得进入最终上游 Prompt。
7. Local 与 S3 历史图片都能通过统一 Asset 读取链路作为上游图片输入。
8. 日志和任务快照能够解释每轮为何选择或未选择历史图片。

## 9. 暂不处理范围

本文仅记录问题和推荐方向。在产品确认上下文默认策略前，不修改现有 Context Selector、数据库结构或 Provider 请求行为。
